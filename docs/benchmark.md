# Benchmark: Sunrise vs vanilla 26.3

`tools/perf_bench.py` measures Sunrise, the vanilla 26.3 client, and vanilla with performance mods on the same machine, world, and camera path, computing every number with the same code. This page says what it measures, how it keeps the comparison fair, what it can't control, and how to reproduce it. The results are in [Results](#results).

## What is measured

One game is started per window size (1280x720 and 1920x1080 by default) and render distance (8, 16 and 32 chunks by default), each from a fresh world, so nothing generated by an earlier run is reused. In each game:

1. **Start to the title screen.** Wall-clock time from starting the process to the first frame of the title screen with no loading overlay.
2. **Create the world.** A creative world named `PerfBench`, seed 1234, default world type and difficulty, created the way the game's own Create World does. **Start to in-world** is the time from starting the process until the player has spawned and every chunk around the spawn is loaded and drawn.
3. **Four scenes**, the paths of `tools/graphics_bench.py`: straight 192-block flights over a village, a forest, the ocean and a mountain. For each scene the player is teleported to the start (time set to noon), held there flying, and the **chunk load time** is the time from the teleport until every chunk in view distance is loaded and drawn. After 2 seconds of settling, the player flies the path at constant speed in 12 seconds (16 blocks per second, faster than sprint-flying), facing along it at the scene's pitch, placed on the line every frame. Chunks are generated and drawn as they come into range during the flight, as in play.
4. **Frame times.** Every frame of every flight is recorded (time between the starts of consecutive frames). From them: average FPS, **1% and 0.1% lows** (the average frame time of the slowest 1% or 0.1% of frames, as FPS: a single long freeze shows), the median, p95, p99 and p99.9 frame times, the slowest frame, and the share of frames in buckets (under 4.17 ms = 240 FPS, 8.33, 16.67, 33.33, 50, 100 ms, and over).
5. **Memory.** The process's resident set size (RSS), sampled 4 times a second from outside the process (`ps` on macOS and Linux, the working set, as Task Manager shows it, on Windows): **peak** over the whole run (startup included) and **steady**, the median during the flights. For vanilla this counts the whole JVM (heap, JIT, native buffers, the integrated server), for Sunrise the whole process. GPU memory where it can be read: Sunrise's own Vulkan allocator total, and what `nvidia-smi` attributes to the process on NVIDIA. On Apple Silicon the GPU shares RAM and no per-process figure is available.

## How it is kept fair

- **Same machine, same run conditions.** Games run one at a time; the load average before and after each run (Windows has none, so it is left out there) and the machine (CPU, RAM, OS) are stored with the results. Runs on a machine doing other work are marked as such and not published.
- **Same settings, one file.** Every game gets the same `options.txt`, written by the driver: render distance, simulation distance 12, unlimited frame rate (`maxFps:260`), VSync off, FOV 70, automatic GUI scale, windowed, no pause on lost focus, and `inactivityFpsLimit:minimized` (both games otherwise drop to 30 FPS after a minute without input). Everything else stays at vanilla's defaults: Sunrise reads vanilla's `options.txt` keys and its defaults match vanilla's (the options harness checks it), and Sunrise's own settings (`sunrise-graphics.txt`) are left at their defaults, which render as vanilla does.
- **Same resolution.** Both games get the same window size, `--width` and `--height` (vanilla's own launch arguments, which Sunrise takes too): 1280x720, the size results were first published at, then 1920x1080, the commonest screen; `--sizes` picks others. The size each game actually renders at is stored with the results: a compositor or screen smaller than the window can shrink it.
- **Same world and path.** Same seed and world type; same paths, yaw and pitch, same flight speed; the same steps in the same order. Vanilla is driven by a small dev-only Fabric mod (`mods/sunrise/src/bench`), which only calls the game's own code: it creates the world with `WorldOpenFlows.createFreshLevel` as the Create World screen does, teleports with `/tp`, sets the time with `/time set`, and places the player on the path each frame as Sunrise's `sunrise-ctl fly` does.
- **Warm-up excluded.** Each scene's flight starts only after its chunks are loaded and drawn and 2 seconds have passed; the load itself is reported separately. JIT warm-up of the JVM during the first scene is part of vanilla's real behaviour and is not removed.
- **The same statistics code.** Sunrise returns its raw frame times (`sunrise-ctl fly ... raw`) and the vanilla mod writes its own; `stats()` in the driver computes every figure for both.
- **Vanilla as players run it.** Your own 26.3 client jar and libraries (as the official launcher installs them for your OS), the official launcher's default JVM arguments (`-Xmx2G` and its G1 options) and the version manifest's JVM flags (`-XX:StackShadowPages=32`, without which vanilla crashes on about half its starts on Windows), Java 25. The game's assets index is not used, so neither game plays sound (Sunrise runs with `SUNRISE_NO_AUDIO=1`, vanilla with OpenAL's null device); textures, models and shaders come from the client jar as usual.
- **Performance mods.** `--game vanilla-mods` adds the Fabric builds for 26.3 of Sodium, Lithium, FerriteCore and ImmediatelyFast, the versions pinned with their hashes in `tools/benchmark-deps/mods.lock.json` (downloaded from Modrinth, never committed), plus Fabric API if one of them needs it.

## Known caveats

- **Fabric Loader is present in the vanilla runs**, to load the driver mod. The only patch it applies is the driver's frame hook, so its cost after startup is negligible, but its mod discovery and class transformation add to vanilla's startup time (the modded runs use the same loader).
- **Readiness is detected differently.** For Sunrise the driver waits until nothing is queued, the chunk counts are unchanged for a second and meshing has gone quiet (fewer than 100 section meshes a second: blocks that change keep being remeshed), and takes the time of the last of these; sections wait for their neighbours' light before they are meshed, so the chunk counts alone stop the clock before the last sections are drawn. For vanilla it waits until the loaded chunk count is unchanged for a second with nothing left to compile, and takes the time of the last change. Both stop the clock within a frame or two of the last section drawn.
- **Locked or headless screens.** A window nobody can see is not composited. On a Mac whose session is locked, Sunrise draws only with `--offscreen` (it renders into a texture and does not wait for the window), and vanilla keeps rendering into its window without it being shown. Such runs measure rendering without presentation and are marked `offscreen`; numbers for players come from runs with the window on a real screen.
- **Different graphics APIs.** Sunrise renders with wgpu (Vulkan on Linux and Windows by default, OpenGL when chosen or when Vulkan has no driver, Metal on macOS); vanilla 26.3 uses OpenGL (or its Vulkan backend when chosen). The backend each game used is stored with the results. This is part of what is being compared.
- **World generation is the same algorithm but not the same threads.** Both generate the same terrain (the parity harnesses check it), with their own threading; the work per chunk differs, which is also part of what is being compared.
- **Variance.** Flights are short (12 seconds), so each configuration runs `--repeats` times (3 by default), each from a fresh world, and every figure is reported as the mean over the repeats with its standard deviation and 95% confidence interval (Student's t). Differences inside the intervals are noise. Lows are the noisiest figures.

## Benchmark your own machine

The game runs the Sunrise half of this benchmark by itself, with nothing else installed:

```sh
sunrise-client --benchmark standard --render-distance 16
```

It starts at the title screen, creates the world `sunrise-benchmark` (seed 1234, creative; the next run replaces it, and it never touches a world it didn't create), flies the four scenes as above, writes a report to `benchmarks/` in the game folder and quits. `--benchmark village` (or `forest`, `ocean`, `mountain`) flies one scene. For the run only, VSync is off, the frame rate unlimited and the game doesn't pause or slow down without focus; your options are not changed. Your other settings (render distance unless given, graphics, window size) are used as they are, and stored in the report, so compare reports with the same conditions.

### A fixed trip

`sunrise-client --benchmark travel` measures what a spawn-only run cannot: the renderer after travel. GPU culling's slowdown only showed after a few hundred blocks, because section ids and arena pages scramble as chunks unload and reload. The run is deterministic: the same seed, path and speed, with the time frozen at noon and the weather clear (`gamerule advance_time` and `advance_weather` off, `weather clear`, `time 6000`), so two runs, or two machines, are comparable. The player is placed at (-960, 150, -176), the view loads, then the camera flies to (-960, 150, 336) in 32 seconds (512 blocks at 16 blocks per second, pitch 30), reported as phase `travel`. It then holds at the end, waits for the view to load and measures four 4-second `hold` blocks. The report's scenario is `travel` and its `repeats` is 4. Besides the figures of the scenes it has `cpu.<phase>.p50_ms` and `gpu.<phase>.p50_ms` for `travel` and `hold` (the median over the hold blocks), so a regression that grows with travel shows in `hold` against a fresh spawn.

`--benchmark-set SWITCH=VALUE` (only with `--benchmark travel`) sets a graphics switch before the world opens: `gpu-culling` (`off`, `on`), `section-cull` (`on`, `off`), `section-sides` (`on`, `off`) or `section-draws` (`flat`, `indirect`), the first value being the default. A switch the device does not offer (`gpu-culling on` where it is not) ends the run with the game's reason and no report. To time a block yourself in any world, `sunrise-ctl bench SECONDS raw` replies with the summary and every frame time.

`--profile` (with `--benchmark`) also records a performance capture of the run, `reports/profile-<time>Z.hzperf` in the game home, with the render thread's call trees, and embeds the report in it verbatim; the game prints both paths. `sunrise-perf query bench FILE` lists the report's metrics and frames from the capture, and `sunrise-perf summary` and `diff` take a bare `benchmarks/*.json` wherever they take a capture ([perf-platform.md](perf-platform.md)). A run longer than the capture's 10 minute window (`standard` on a slow machine) ends the capture early and keeps the report out of it.

### Compare a setting

`sunrise-client --benchmark ab:SWITCH` tells whether one renderer setting changes the frame time, or only the noise of the machine. It runs the trip of `travel` with the switch's B value set before the world opens, then measures 8 pairs of 4-second blocks in the order B A A B B A A B..., each after 2 seconds at that arm that are discarded and with the time reset to noon before each pair. Neighbouring blocks are in different arms and the order alternates, so drift (heat, streaming finishing, other programs) cancels. Afterwards each arm's render passes are timed once (`gpu_pass.ab_a.<pass>_ms`, `gpu_pass.ab_b.<pass>_ms`), and the setting is put back to what it was before the run, also when the run fails. It takes about 3 minutes.

| `SWITCH` | A (the default) | B |
| --- | --- | --- |
| `gpu-culling` | `off` | `on` |
| `section-cull` | `on` | `off` |
| `section-sides` | `on` | `off` |
| `section-draws` | `flat` | `indirect` |

```sh
sunrise-client --benchmark ab:gpu-culling --render-distance 12
sunrise-ctl --socket $PWD/ctl.sock launch --offscreen --benchmark ab:gpu-culling
python3 tools/bench_stats.py benchmarks/game-*-ab_gpu-culling.json
```

The game quits when it is done, so `launch` without `--wait` is enough; the report is under `benchmarks/` in the game folder.

The report's scenario is `ab:SWITCH`, its `repeats` the number of blocks (16) and its `warmup_s` 2. The blocks are `frames` entries with phase `ab.a` or `ab.b`, and the report's `ab` field holds the result for the GPU, CPU and frame time of a frame: B minus A, a 95% interval and a verdict (`slower`, `faster`, `negligible`, `within_noise`), computed as described in [the report format](benchmark-report.md). A difference inside the interval around 0 is noise. `ab.first_block_outside_range` is true when the first B block, the only one measured before any switch, lies outside the later B blocks: switching reset part of what the trip built (turning GPU culling on rebuilds its records from the renderer's resident order, which can undo the scrambled ids of the trip), so the comparison may understate the difference. A switch the device does not offer (`gpu-culling on` where it is not) ends the run with the game's reason and no report.

The report is the [benchmark report format](benchmark-report.md): startup to the title screen and to in-world, each scene's chunk load time, chunks generated and section meshes built, every flight's frame figures and histogram, resident and GPU memory, the binary's size, and the machine (OS, CPU, RAM, GPU, driver, backend, display), the load average before the run and whether it ran on battery. If you allowed benchmark uploads (the launcher's data collection choices, [docs/telemetry.md](telemetry.md)), the same report, dated to the day and without local fields, is kept for the launcher to send; otherwise it stays on your machine.

## Reproduce it

You need Sunrise built (`cargo build --release -p sunrise-game -p sunrise-client-lib --bins`) and its resources prepared from your own copy of 26.3 (which also provides `.local/minecraft/26.3`, the vanilla client the driver starts), Java 25 with `javac`, and Python 3.11 or newer.

```sh
python3 tools/perf_bench.py --game sunrise --label sunrise-mine
python3 tools/perf_bench.py --game vanilla --label vanilla-mine
python3 tools/perf_bench.py --game vanilla-mods --label mods-mine
python3 tools/perf_bench.py --table sunrise-mine vanilla-mine mods-mine
```

Options: `--distances 8,16`, `--sizes 1920x1080`, `--scenes village,ocean`, `--seconds 20`, `--repeats 5`, `--heap 4G` (vanilla), `--offscreen` (Sunrise, for locked or headless sessions). Results go to `benchmarks/perf/<label>-rd<N>.json` at 1280x720 and `<label>-1080p-rd<N>.json` at 1920x1080 (other sizes `<label>-<W>x<H>-rd<N>.json`; `--table` takes those labels), one [benchmark report](benchmark-report.md) per window size and render distance (the same format the game's `--benchmark` and the launcher write), with the load average before each game; each game's log, and the vanilla driver's event log, stay in `.local/perf-bench/`. Keep the machine otherwise idle, plugged in, and the window on a screen. `PERF_BENCH_TRACE=<file>` appends each load's timeline to that file, one JSON line per sample: Sunrise's status every 50 ms after a line for each teleport (resident and generated chunks, chunks still pending, stage counts), and the vanilla driver's loaded chunk count and the chunks it holds within the render distance minus one; compare when the columns arrive with when the load ends.

### Many-entity stress scenes

`--scenes stress` (or some of `stress_empty`, `stress_mobs`, `stress_items`, `stress_frames`, `stress_armor_stands`, `stress_chests`, `stress_signs`, `stress_banners`, `stress_particles`) runs the scenes of `tools/stress_scenes.py` instead of flying: 1000 still mobs of 8 kinds, 2000 dropped items, 512 item frames, 500 armoured armor stands, 800 chests and shulker boxes, a wall of 687 written signs, 300 banners, and steady particles from repeating command blocks (flames, smoke, end rods, firework bursts, TNT in the air). Each is built high above the terrain by the same vanilla commands in every game (Sunrise through `sunrise-ctl command`, vanilla and vanilla-mods through the driver mod), settles 6 seconds and is held still for `--seconds`; `stress_empty` is the same camera and floor without them. Entities are drawn only within a distance that grows with the render distance up to 20 (`Entity.shouldRenderAtSqrDistance`), so run them at 16 or more:

```sh
python3 tools/perf_bench.py --game sunrise --scenes stress --distances 16 --label stress-sunrise
python3 tools/perf_bench.py --game vanilla --scenes stress --distances 16 --label stress-vanilla
python3 tools/perf_bench.py --table stress-sunrise stress-vanilla
```

Besides the FPS table, `--table` then gives each scene's median frame CPU time (Sunrise), client tick time and resident memory. Chests stay closed: opening them needs a player, which neither driver has. The stress scenes use 26.3's command syntax, so they are not for `--game neoforge`.

### Comparing two builds

`--compare BEFORE AFTER` runs games of two build folders alternately, in the order B A A B B A A B..., which
counterbalances the order within each block of four games; pair *k* is games 2*k* and 2*k*+1. `--repeats` is the number
of pairs per render distance and window size: even, so the blocks are whole, and at least 6, which the interval needs.
Each figure of each scene goes through `sunrise_bench::compare`'s statistic ([benchmark-report.md](benchmark-report.md)):
the Hodges-Lehmann estimate of after minus before, its exact signed-rank 95% interval (nominal, for independent and
symmetric pair differences) and the verdict.

- **Gated:** frame time p50 and p99, and the server thread's tick time p50 and p99; `menu_hold` gates frame time only,
  because Options may pause the integrated server.
- **The rule:** a gated figure passes when its point estimate, computed from unrounded values plus how far rounding can
  move it (half of 0.1 ms for tick times), is at most `--budget` percent (default 3, #2510's pooled gate) of the before
  figure. Its interval is reported beside it ("ci95 within 3%"): a wide interval around no change is noise to report,
  not a slowdown. A gated figure any game lacks fails (`missing`).
- **Why not the interval:** `/tick query` sees only the server's last 100 ticks, in 0.1 ms steps, however long the
  flight, so tick intervals are wider than 3% on one machine unless the run has many more pairs (hours per scene).
- **Reported, not gated:** CPU and GPU frame p50.
- **Output:** the table on the terminal; the workload (scenes, seconds, `--graphics`, packs), each game's build, start
  and end times and figures, and the results in `benchmarks/perf/<label>-compare-rd<N>.json`. The exit status is 1 when a
  gated figure fails.

```sh
python3 tools/perf_bench.py --compare target-base/release target/release --budget 3 --repeats 6 --distances 16 --offscreen
```

The server tick figures are vanilla's `/tick query` after each flight: the integrated server's last 100 ticks, in 0.1 ms
steps. They count only when all 100 fall inside the flight (`--seconds` 5 or more at 20 TPS); otherwise they're missing.
A joined server's ticks aren't read, so `--compare` runs single player. When rounding alone (half a 0.1 ms step) is more
than the budget allows, a before tick time under about 1.7 ms at 3%, the row says "below resolution: not gated": it is
shown, but neither passes nor fails, and the scene's frame figures are gated as usual. A missing tick figure still fails.

Set-up options for Sunrise: `--graphics KEY:VALUE` (a line of `sunrise-graphics.txt`, repeatable), `--resource-pack PATH`
(turned on in `options.txt`, repeatable) and `--shader-pack PATH` (picked through `SUNRISE_SHADER_PACK`, a folder or a
zip); a report records them under `conditions`. `--scenes menu_hold` holds the Options screen open for `--seconds` at the
village flight's start while Tab steps the focus every 250 ms (#2498's menu path), on fixed deadlines. The taps go through
the control socket's `key`, which reaches the Options screen's own key handling but not the window's keyboard-focus
driver (`key_focus_key`); no control command older builds have reaches that driver.

On Windows, run `python tools\perf_bench.py ...` the same way. Sunrise's control endpoint there is a localhost TCP port, which the game writes to a `.json` file in the temporary folder. `--build` can point at an installed release (`%APPDATA%\sunrise-launcher\versions\vX.Y.Z`, with `--resources` its `.local\sunrise-client\26.3`), and the report then gives that release's version.

## Frame pacing

`tools/pacing_bench.py` measures smoothness rather than throughput: every frame of the sessions where players see
hitches, a fast flight (64 blocks a second over new terrain), eight long teleports, trips to the Nether and back, and
the inventory and pause menu opened and closed twenty times. For each it reports the median, p99 and p99.9 frame
times, the slowest frame, the 1% and 0.1% lows and the frames over 33 ms. The game runs with `SUNRISE_SPIKES`, so
its slow ring keeps every slow frame's timed spans (wall and thread CPU time), and a client capture (`profile client start`) records each scenario: the report keeps the 12
slowest frames' spans, read with `sunrise-perf query ticks`, next to the figures, which says whether a hitch was work (a
span's CPU time) or waiting (the GPU, a lock, a file). Build `sunrise-perf` beside the game first
(`cargo build --profile fast -p sunrise-perf`, or pass `--perf`). The ring holds 256 frames, and the threshold (`--spike-ms`, 20 by default) is on the frame's wall time.
`Renderer`'s frame and `entity_geometry` time their steps as spans too (`spans::laps`).

```sh
python3 tools/pacing_bench.py --build target/fast --label main --distances 32
python3 tools/pacing_bench.py --compare main mybranch
```

`--size 320x180` keeps a software renderer (Mesa's lavapipe on a machine with no GPU) from hiding the CPU side; there
only the spans' CPU times mean anything.
